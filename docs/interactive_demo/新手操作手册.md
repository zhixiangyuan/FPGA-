# AFDX 新手操作手册

本手册教你使用 `D:\FPGA\功能演示` 中的测试入口，完成实际 RTL 仿真并向评委展示结果。每项都提供可直接使用的数据、按钮顺序、预期变化和讲解示例。界面已预填可用数据；打开后可以直接测试，也可以修改后测试。

## 先看这里：怎样完成一次测试

1. 关闭上一项实验的中文窗口及它对应的 ModelSim，再双击本项 `.cmd` 文件。一次只演示一个入口。
2. 等待上方出现「等待本人操作：仿真已加载并停在 100 μs」。首次编译可能需要几十秒。100 μs 是暂停位置，不是报错。
3. 按本手册点击按钮。出现「真实仿真运行中」后，等待完成，不要连续重复点击。
4. 完成后先看「本次操作」和「功能核对」，再看本次实际接收、响应值或计数变化，最后看性能指标。
5. 每次点击后的结果会替换上一次结果；「本次」只统计这次操作，「本会话累计」才是从窗口启动至今的总数。结果框有滚动条，可以向下查看。
6. 需要重新从默认状态开始时，关闭本项中文窗口和对应 ModelSim，再重新双击入口。重新启动会复位序号、管理值和统计，旧日志保留。

修改输入框的方法：点击输入框 → 按 Ctrl+A → 输入新值。仅修改输入框不会启动测试。修改链路下拉框后，必须点击「应用所选故障／恢复」才生效。

每次启动只编译和仿真，不需要操作开发板。不要点击 Implementation、Bitstream 或 Download。手动演示、自动实施验证与完整正式验收是不同记录，本手册介绍的是有限场景 RTL 演示。

## 结果怎样读

| 结果行 | 直白解释 |
|---|---|
| 功能核对：通过 | 实际收发字节、校验、序号和适用的管理响应与独立参考一致。错误帧被正确拒收也能通过 |
| 本次计数变化：发送 +1；交付 +1 | 这次提交并发出一帧，应用接收到一帧 |
| 发送 +1；交付 +0 | 发出了，但本次没有应用交付。结合双网断开、错误注入、序号异常判断 |
| 本次实际接收：无新数据 | 这次没有收到新的应用消息。不会再用旧消息充当本次结果 |
| 消重 +1 次 | A、B 两份有效副本最终只向应用交付一次 |
| 业务解析器拒绝 A/B | 普通业务解析器拒绝的数量，不是 SNMP 失败总数。SNMP 应看请求/响应与实际响应值 |
| 实际测量值；达标状态 | 功能通过与性能达标分开显示。只评价已测样本，不代表任意负载下都达标 |
| 只有实测值，没有达标标签 | 本项没有明确数值判据，或本次不是适合评价该项的负载；只展示测量结果 |
| 未测量／样本不足 | 尚无足够测量数据，不给出达标结论 |

性能结果不列比赛要求数值。有充分依据的项目只显示「达标」或「未达标」；其他项目仅显示实测值或样本情况，不附达标状态。吞吐在 07 的完整正常批量负载中判断；01 的短消息、03 的故障负载只显示吞吐实测值。时延是应用输入首字节至输出末字节；未交付帧没有可用时延。同 VL 同长度极差至少需要两帧；比赛资料未给精确数值门槛，因此仅显示实测值。RTC 的模拟校时不证明绝对 UTC 精度。

## 01 业务收发与帧格式：输入什么，就收到什么

**打开：** `01_业务收发与帧格式演示.cmd`。

**测什么：** 应用数据能否经过封装、双 MAC 发送、测试链路、接收校验和消重后原样交付。

### 第一次：直接使用默认数据

| 输入框 | 默认值 |
|---|---|
| VLID（十六进制） | `1234` |
| 单帧数据（UTF-8） | `HELLO_FPGA` |

1. 等待加载完成。
2. 点击「发送本人输入的数据」。
3. 等待「本次独立核对通过」。
4. 看结果：发送 +1 帧、交付 +1 帧，实际接收为 `HELLO_FPGA`，VLID 为 `0x1234`，载荷为 10 字节。正常双网下消重增加 1 次。

### 第二次：修改数据，让变化明显

1. 将 VLID 改为 `1235`。
2. 将单帧数据改为 `FPGA_0123456789_ABCDEFGHIJKLMNOPQRSTUVWXYZ`。
3. 再点「发送本人输入的数据」。
4. 看实际接收变成新内容，VLID 变成 `0x1235`，载荷变成 42 字节，HEX 与最近发送帧的 FCS 随内容变化。不同 VL 各自维护 SN，因此新 VL 的 SN 不必接着上一 VL 增加。

**看波形：** 在 ModelSim 查看 `tx_data`、`tx_valid`、`rx_data`、`rv`、`rs`、`re`。`rv` 高时 `rx_data` 才是有效接收数据，`rs/re` 标记首尾。两次载荷不同，数据值不同；第二条更长，有效数据持续时间也会更长。程序自动缩放最近接收附近，两幅图的比例尺可能不同，比较宽度时先保持相同时间刻度。单帧时没有同 VL 间隔样本是正常的。

**向评委讲：**「我先发送一段短消息，再修改通道和内容。接收端读回相同内容，长度和字节值随输入改变，双网副本只交付一次。」

## 02 多 VL 与 BAG 调度：四个通道轮流发送

**打开：** `02_多VL与BAG调度演示.cmd`。

**测什么：** 多个通道能否分别发送并交付，同一通道相邻帧的实际发送间隔是否符合当前 BAG 配置。

| 输入框 | 默认值 |
|---|---:|
| VLID（十六进制） | `1234` |
| 批量帧数 | `32` |
| 批量 VL 数 | `4` |
| 每帧有效载荷字节数 | `64` |
| 应用输入间隔 | `33000` |

1. 等待加载完成。「单帧数据」在本项批量测试中不使用，保留默认值即可。
2. 点击「确认参数并生成批量负载」，不要点上面的单帧发送按钮。
3. 弹窗应是 32 帧、4 VL、64 字节、33000 周期；点击「是」。
4. 等待完成。看「本次计数变化」应为发送 +32、交付 +32。
5. 看「本次各 VL 交付」：`1234=8 帧；1235=8 帧；1236=8 帧；1237=8 帧`。
6. 看「本次同 VL 最小发送间隔」的实际毫秒值和达标状态。极差在相同 VL、相同长度内统计。本项的小包吞吐只测量，不作为持续性能达标测试。

**修改后再测试：** 只把「批量 VL 数」改为 `2`，其他参数不动，再点批量按钮并确认。本次各 VL 应变成 `1234=16 帧；1235=16 帧`，本次总交付仍为 32。累计数会继续增加，不要把累计数当作本次帧数。

**看波形：** `a/b` 是双网发送字节，`ae/be` 高表示发送有效，`dut/app_sent`、`dut/rx_delivered` 是累计计数。若要看整个批次，在 ModelSim 点 Zoom Full，再放大本次发送区间；自动定位只展示最后一帧附近。输入轮转不保证所有通道在最终线上严格按编号排列，实际发送由调度器决定。

**向评委讲：**「32 帧在四个通道间轮流提交，每个通道交付八帧。同一通道的发送间隔由实际线上时刻核对，改变通道数后，各通道的交付分布随之变化。」

批量数据由测试环境按公开公式生成，不是单帧文本框的重复内容。数据公式为 `(53 + 帧号×13 + 字节位置×37 + (字节位置>>2)) mod 256`，结果显示二进制载荷和 HEX 是正常的。

## 03 双网故障与消重：单网仍能收到，双网断开收不到

**打开：** `03_双网故障与消重演示.cmd`。本组从新窗口开始，VLID 保持 `1234`。

**测什么：** 正常双网只交付一次；单网断开后另一网仍能交付；双网断开时不交付；A 接收错误时 B 仍可交付。

每一行都按「选链路 → 点应用 → 等完成 → 填消息 → 点发送 → 等完成」操作。不要只改下拉框就直接发送。应用链路只改变状态，不发送消息；这时计数不增加是正常的。

| 顺序 | 链路选择 | 单帧数据 | 发送后重点看什么 |
|---|---|---|---|
| 1 | 双网正常（初始状态已生效） | `NET_TEST`（默认） | 发送 +1、交付 +1、消重 +1，实际收到 NET_TEST |
| 2 | 断开 B，仅 A | `ONLY_A` | 发送 +1、交付 +1，实际收到 ONLY_A |
| 3 | 断开 A，仅 B | `ONLY_B` | 发送 +1、交付 +1，实际收到 ONLY_B |
| 4 | A 接收错误，B 正常 | `A_ERROR_B_OK` | A MAC 丢弃 +1、B MAC 丢弃 +0，仍交付 +1 |
| 5 | 双网正常 | `RECOVER_OK` | 交付 +1，实际收到 RECOVER_OK；消重和序号计数按真实恢复状态显示 |
| 6 | 双网断开 | `NO_DELIVERY` | 发送 +1、交付 +0，明确显示「本次实际接收：无新数据」 |

第一行可直接点发送；后五行必须先点「应用所选故障／恢复」。先看「已生效链路」确认切换成功，再发送对应消息。

**为什么仍有波形：** 断开的是测试链路的返回方向，不是关闭整个设备。时钟、应用输入和 A/B 发送端仍可有波形；要看接收是否有效、交付计数是否增加，不能看「有波形」就判断收到。无新接收时，程序定位最新发送或注入附近，不再自动跳回旧接收帧。

**为什么恢复后可能第一条不交付：** 同一网络连续错过多帧，恢复时可能触发序号检查。当前实现会拒收异常跳号并更新该网络的序号状态，后续帧可能恢复交付。界面会显示本次序号异常增量，不把旧数据伪装成新数据。不要通过连续点击掩盖这一现象。想做独立的新实验，将 VLID 改为本会话未用过的 `1235`，或重启本项。

**看波形：** `mask` 是已生效链路，`3` 为双网、`1` 为仅 A、`2` 为仅 B、`0` 为双断；`error_a` 为 A 错误注入。`rv` 是应用接收有效，`dut/rx_delivered` 是交付计数。`net_valid` 是测试环境内部数据流，不代表断网后 DUT 一定收到。跨操作查看时保持正确时间区间。

**向评委讲：**「我断开任意一条链路，新的消息仍能交付；双网同时断开，发送仍增加，但没有新交付。结果显示的是本次变化。」

## 04 错误校验与异常序号：错误报文不能进入应用

**打开：** `04_错误校验与异常序号演示.cmd`。默认 VLID 为 `12A0`、数据为 `CHECK_TEST`、SN 为 `1`、类型为「正常报文」。

**测什么：** 分别验证 MAC 校验、IP 校验、UDP 长度和序号检查。这里的按钮模拟对端发送完整报文，方向是「对端 → 本设备」，不是应用发送。

每一行都先修改三个输入项，再点击「注入本人选择的对端报文」，等待完成后看结果。

| 顺序 | 报文类型 | SN | 对端数据 | 应看到的本次效果 |
|---|---|---:|---|---|
| 1 | 正常报文 | 1 | `CHECK_TEST` | 交付 +1，实际收到 CHECK_TEST |
| 2 | FCS错误 | 2 | `BAD_FCS` | 无新数据；MAC 丢弃 A/B 各 +1 |
| 3 | IP校验错误 | 2 | `BAD_IP` | 无新数据；业务解析器拒绝 A/B 各 +1 |
| 4 | UDP长度错误 | 2 | `BAD_UDP` | 无新数据；业务解析器拒绝 A/B 各 +1 |
| 5 | 正常报文 | 2 | `GOOD_FRAME` | 交付 +1，实际收到 GOOD_FRAME，说明前面的错误帧没有污染正常序号 |
| 6 | 正常报文 | 9 | `BAD_SN` | 无新数据；本次序号异常增加，两网各检查一次 |
| 7 | 正常报文 | 10 | `NEXT_OK` | 交付 +1，实际收到 NEXT_OK，说明按当前序号策略继续接收 |

做第二至第四行时，SN 都保持 2。第五行仍用 2；第六行改成 9；第七行改成 10。不要每次随意增加，否则不是表中的实验。

本项「发送 +0」是正常的：没有从应用发送口提交业务帧。注入到接收端的报文和计数变化才是本项结果。IP/UDP 错误报文仍有正确的 Ethernet FCS，以便分别测试协议校验。

**看波形：** 错误帧仍有输入波形，但应用侧 `rv` 不产生对应有效消息；看 `dut/mac_a_dropped`、`dut/parser_a_rejected` 或 `dut/rx_integrity_errors` 增加。正常帧时 `rv` 有效，交付计数增加。上方「功能核对：通过」表示实际行为与所选错误类型相符，不能理解成错误帧也被接收。

**向评委讲：**「相同序号下，我先注入不同错误报文，再注入正确报文。错误被对应层拒收，正确数据才进入应用；跳号报文也不能直接交付。」

## 05 SNMP 管理读写：写入新值，再读回新值

**打开：** `05_SNMP管理读写演示.cmd`。默认对象 `4 · sysContact`，SET 值 `FPGA_TEST_2026`。

**测什么：** 通过真实管理报文读设备信息、修改信息、再从实际响应中读回。GET 是读取，SET 是写入；只在框里改文字不会写入设备。

1. 等待加载完成，保持默认对象。
2. 点击「GET：从真实响应读取」。看「实际 SNMP 响应值」为初始值 `afdx-es-team3`，本次请求/响应为 +1/+1。
3. 保持默认 SET 值 `FPGA_TEST_2026`，点击「SET：写入本人填写的值」。看「本次 SET 输入」和「实际 SNMP 响应值」都是 FPGA_TEST_2026。
4. 再点击 GET。实际响应值仍为 `FPGA_TEST_2026`；这一步才证明重新读取的是保存后的值。
5. 想让变化更明显，把 SET 值改成 `TEAM_AFDX_01`，再点 SET，再点 GET；实际响应值应变成 TEAM_AFDX_01。

更换对象时，`5 · sysName` 初始值为 `afdx-s2`，`6 · sysLocation` 初始值为 `AFDX lab bench`。每个对象各自保存。重启后恢复初始值。

**数据限制：** SET 只支持 1～32 个 ASCII 字节，可填英文、数字、英文标点和空格。不要填「我爱FPGA」；可以填 `I LOVE FPGA`。中文会在执行前被拒绝，不会写入 DUT，不用重启。

**不要误读计数：** 应用发送/交付为 0 是正常的，SNMP 走管理路径。业务解析器拒绝 A/B 可能各增加 1，因为这条管理报文不属于普通业务配置；管理路径仍可正常处理。看实际响应值、错误状态为 0，以及本次请求/响应 +1/+1。结果还显示请求首字节至响应末字节的实测耗时；没有单独数值判据时不判定其性能达标。

**看波形：** `dut/snmp_requests`、`dut/snmp_responses` 每次操作增加。`rx_data/rv` 是业务应用输出，不用于显示 SNMP 返回字符串；本项优先展示中文结果中的实际响应值。

**向评委讲：**「这是设备联系人信息。我先读初始值，再写入自己的值，最后重新读取。这里展示的字符串来自实际响应报文，不是仅显示输入框里的内容。」

## 06 RTC／SNTP 网络校时：同步标志由 0 变为 1

**打开：** `06_RTC与SNTP网络校时演示.cmd`。默认服务器偏移为 `250` 微秒。

**测什么：** 设备发出时间请求后，能否处理模拟服务器的响应，使用四个时间戳计算 offset、delay 并更新 RTC。

1. 等待加载完成。设备已自动发出时间请求，但尚未收到测试环境的时间响应。
2. 保持偏移 `250`，点击「发送本人确认的时间响应」。
3. 等待完成。看「RTC 同步状态：0 → 1」和「四时间戳计算核对：通过」。
4. 看「实际 RTC offset」和「delay」的实测微秒值。这两个值不要求等于输入框的 250；输入值只是构造服务器时间戳的参数。
5. 要比较另一组参数，关闭本项两个窗口，重新启动 06，改填 `500` 再发送。比较两次实际 offset；不要在同一会话重复发送，当前入口每次只响应一次自动请求。

**看波形：** `ts` 是同步标志，应从 0 变 1；查看 RTC UTC、`sntp_t1` 至 `sntp_t4`。这些时间戳以 NTP Q32.32 格式记录，不是直接显示微秒的普通整数。

offset 按 `(t2−t1+t3−t4)/2`、delay 按 `(t4−t1)−(t3−t2)` 重算核对。服务器由测试环境模拟；绝对 UTC 精度显示「未测量」，不能说已连接真实互联网时间服务器或证明某种绝对精度。

**向评委讲：**「设备先发出时间请求，我再提供模拟服务器响应。同步标志由零变一，设备实际计算的 offset 和 delay 通过独立四时间戳核对。」

## 07 吞吐、时延与极差：用批量数据测性能

**打开：** `07_吞吐时延与极差演示.cmd`。使用新会话，不混入其他手动故障实验。

**测什么：** 当前正常批量负载的有效载荷交付吞吐、应用到应用最大观测时延，以及同 VL 同长度的时延极差。

| 输入框 | 默认值 |
|---|---:|
| VLID | `1234` |
| 批量帧数 | `64` |
| 批量 VL 数 | `16` |
| 每帧有效载荷字节数 | `1471` |
| 应用输入间隔 | `8100` |

1. 保留默认值。单帧文本框与本次批量无关。
2. 点击「确认参数并生成批量负载」，在弹窗核对后点击「是」。
3. 等待完成，看发送 +64、交付 +64、未交付 0。各 VL 分别交付 4 帧。
4. 看「本次有效载荷交付吞吐」的 Mbps 实测值和状态；再看「最大观测时延」的 μs 实测值和状态。
5. 看「同 VL 同长度时延极差」与「同 VL 最小发送间隔」。记录本次数据，不把历史报告数值当成本次结果。

**修改后比较：** 想观察输入变慢时的吞吐变化，重启 07，保持其他默认值，只将输入间隔改为 `33000` 再测试。实际吞吐应降低；若显示「未达标（本次负载）」表示这组较慢输入下未达到吞吐门槛，不表示正常默认负载也失败。不要用两组不同输入去宣称设计优化收益。

**统计含义：** 吞吐只计一次有效载荷，不把 VLID、协议头和 A/B 副本当作双倍数据；窗口从本次第一帧输入首字节到最后一帧输出末字节。时延包含队列、调度、测试链路和接收处理；最大观测值只是本次样本最大值。极差在同 VL、同长度组内先算最大减最小，再取最大组值，不混不同通道和长度。每组不足两个样本就显示样本不足；不显示为零抖动。

**看波形：** `ae/be` 有一组组发送活动，`dut/app_sent`、`dut/rx_delivered` 持续增加。自动定位最后接收附近；查看完整批次用 Zoom Full。吞吐不能靠波形看起来「很密」判断，以结果中的计算值为准。

**向评委讲：**「本次用十六个通道发送六十四帧，先确认完整交付，再按真实输入输出时刻计算吞吐和时延。界面列出本次实测值和达标状态。」

## 08 调度优化前后对照：相同输入，两套新仿真

**打开：** `08_调度优化前后对照演示.cmd`。

**测什么：** 在固定管理积压压力下，只改变发送仲裁器，对比两套设计的新实测结果。

1. 等待两套 ModelSim 均加载并停下。固定条件为 24 帧、16 VL、1471 字节、8100 周期输入间隔，并含两个管理请求突发；无需填参数。
2. 点击「确认条件并开始两套新仿真」，在弹窗点击「是」。
3. 等待「本次对照 PASS」。查看优化前、优化后的吞吐、最大观测时延、极差，以及吞吐和时延的变化百分比。
4. 看输入一致性核对结论。任何一侧失败或实际输入不一致，都不能当成有效优化对照。

此处使用已验证配套的历史生产 RTL 快照，两侧仅仲裁器不同；01～07 使用当前活动 RTL。当前流水化 MAC 与旧仲裁器不能直接混编，因此 08 不代表当前所有 RTL 的优化收益。两个管理请求突发用于刻意形成排队压力，不属于正常对端 BAG 负载，吞吐/极差的达标状态不作常规性能结论。实际收益以新仿真为准，不承诺固定百分比。

**向评委讲：**「两套设计接收相同字节和相同时刻的输入，只改变仲裁器。本次管理积压压力下，比较它们的实际吞吐和最大观测时延。」

## 常见问题与处理

| 现象 | 先做什么 |
|---|---|
| 改了链路后没有变化 | 点击应用按钮，等完成，核对已生效链路，再发送新消息 |
| 数据框改了，结果没变 | 修改文字不会运行；点击对应发送、SET 或注入按钮 |
| 要连发两次才收到 | 看本次序号异常是否增加；恢复网络可能先拒收跳号。换未用过的 VL 或重启做独立实验 |
| 无新接收但还有波形 | 时钟和发送仍活动；看 rv 与本次交付，不看有没有线条 |
| SNMP 业务解析器拒绝增加 | 看实际 SNMP 响应值和请求/响应，不把业务解析器计数当管理请求失败 |
| 输入中文 SET 被拒绝 | 换 ASCII 字符，点确定后重新 SET；不用重启 |
| BAG 或极差显示样本不足 | 同一 VL 至少要有两帧；使用 02 或 07 默认批量 |
| 功能通过但吞吐未达标 | 功能正确与性能达标是两回事；核对本次负载是否是 07 默认条件 |
| 编译或仿真超时、功能失败 | 停止此项，保留本次日志和失败原因，不把该段当作成功证据 |
| 界面仍是旧版 | 关闭旧中文窗口及对应 ModelSim，重新双击入口。运行中的 Python 不会自动加载新代码 |
