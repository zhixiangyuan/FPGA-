# 阶段2 管理服务系统集成验收

以下是管理服务在真实MAC链路上的集成结果，不代表阶段2系统完整通过。

## 范围与结构

管理路径在集成顶层中复用同一套冻结MAC与共享帧构建器，包含六个开发模块：`rtl/afdx_service_message_fifo.v`（单条服务消息缓冲与描述符优先回放）、`rtl/afdx_service_tx_arbiter.v`（业务回环、SNMP应答与时务请求三路共享发送口，两个服务源之间轮转）、`rtl/afdx_management_rx_demux.v`（按目的端口161与源端口123分流管理VL，其他端口排空）、`rtl/afdx_sntp_client.v`（RFC4330时务客户端）、`rtl/afdx_rtc_timebase.v`（UTC Q32.32时基与四时间戳同步运算）、`rtl/afdx_stage2_mgmt_top.v`（16 VL业务回环加两条专用管理VL的集成顶层）。

管理 VL 为 `0x1244`（SNMP，端口 161），时务 VL 为 `0x1245`（SNTP，端口 123）。管理器 MAC `02000000000a`、IP `10.0.0.9`；工程约定管理站兼任时间服务，因此 SNTP 服务器 IP 与管理站相同而端口不同，管理 VL 的对端校验保持单一比较，管理解析器只需覆盖 `[0x1244, 0x1246)` 连续区间。

两条服务路径各自独占一个不背压的消息缓冲。共享 MAC 接收路径上不允许出现来自服务端点的停顿：服务缓冲一旦反压，就会经分流、完整性门与解析器传导到 MAC 的接收许可，进而阻塞全部业务 VL，这正是下文缺陷 1 的成因。

## 系统运行结果

`build/logs/mgmt_016` PASS：ModelSim 退出码 0、Errors 0、Warnings 0。57 个 Golden 用例中 56 个 GMII 输入帧共 6894 线字节同时驱动 16 VL 业务路径与管理路径，47 个输出帧、6484 线字节逐字节匹配独立 Python Golden（含前导码、SFD 与 FCS）。

| 项 | 实测 |
|---|---:|
| 输出帧 / 线字节 | 47 / 6484（与 Golden 一致） |
| SNMP 响应帧 | 44 |
| SNTP 请求帧 | 1 |
| 业务回环帧 | 2 |
| 管理 VL（0x1244）BAG | 最小 139969、最大 560380 周期（要求 125000） |
| 业务 VL（0x1234）BAG | 145747 周期（要求 125000） |
| 时务 VL（0x1245）帧数 | 1，尚不构成间隔 |
| GMII 输入首字节至输出首字节 | 2.880 µs 至 48.256 µs |

负面用例按预期分离：非管理端口 9999 被 demux 排空并计数 1；重复序列号被管理 VL 完整性门拒绝 1；非授权对端 `10.0.0.11` 被管理解析器拒绝 1。50 个 SNMP BER 用例经真实链路传输，其中 44 个产生响应、含 14 个协议错误响应，全部输出帧逐字节匹配 Golden；其余请求按协议预期保持静默。

## 时务与 RTC 系统集成

时务交换由测试在复位释放时触发，因此客户端锁存的请求起点就是 RTC 的复位初值，请求报文的 origin 字段与 Golden 完全一致，不需要在仿真期回读。服务器应答由 Golden 生成并经真实 GMII 接收端口注入，与 SNMP 请求走同一套管理解析、完整性门与端口分流逻辑。

| 项 | 实测 |
|---|---|
| 请求起点（T1） | `e900000000000000`（RTC 复位初值） |
| 服务器接收 / 发送（T2 / T3） | `e900000000100000` / `e900000000100abc` |
| 客户端接收（T4） | `e9000000007deed4`（应答首字节时刻的 RTC 读数） |
| SNTP 接受 / 拒绝 / 超时 | 1 / 0 / 0 |
| 往返延迟 | 8250392 NTP 单位（约 1.921 ms），限值 1 秒 |
| 偏移 | -3076620 NTP 单位 |
| RTC 同步 | `synchronized=1`、`sync_count=1`、`error_count=0` |

`scripts/run_stage2_mgmt.py` 不复用仿真器内部结果：它用 Golden 给定的 T1、T2、T3 与仿真记录的 T4 重新做 NTP 模运算，独立算出往返延迟与偏移，再与 RTC 寄存器比对，二者一致。T4 是仿真内部量（取决于应答注入时刻），由测试导出后参与该算式的校验，不作为可预测量。

## 修复的真实缺陷

1. 服务消息 FIFO 原来只在空闲状态接受字节，收到首字节后即离开空闲，第二个字节永不接收，输出端永久等待；上游 demux、完整性门与解析器依次停顿，共享 MAC 的接收就绪被拉低，导致 55 帧中 49 帧被 MAC 丢弃。现改为捕获期间持续接受，超长消息按溢出计数丢弃，不再阻塞共享接收路径。
2. 管理 BAG 原设 12500 周期（100 µs）。AFDX 合法 BAG 为 1、2、4 至 128 ms，共享构建器按设计拒绝该描述符，服务帧因此无法建立。现采用最小合法 BAG 1 ms（125000 周期）与 10% 抖动，未修改已验证的构建器。
3. 集成顶层把接收解析器的 `payload_vlid` 输出与回环队列的 `msg_vlid` 输出接到了同一个网 `biz_vlid`。两个驱动值不同时该网为未知值，构建器的 `desc_legal` 随之为未知，`desc_fire && !desc_legal` 与 `legal_desc_fire` 两个条件都不成立，业务描述符既不发帧也不报错。现解析器改用独立网 `biz_rx_vlid`。
4. 时务客户端接到的接收时刻取自一个寄存输出，比应答首字节晚一拍，客户端锁存的 T4 恒为 0；RTC 因此判定 `network_elapsed<0` 而拒绝同步（`error_count=1`）。现改为在首字节周期直接给出 RTC 读数，寄存器版本仅供观测。
5. 共享构建器的 VL 槽位原为 17 个（`0x1234` 起 16 个业务加 `0x1244`），时务 VL `0x1245` 超出范围会被按非法 VL 拒绝；现扩为 18 个槽位。

## 校验脚本修正

线帧 VLID 的取字节位置改为 DA 低两字节（帧含 8 字节前导码与 SFD）。解析器拒绝计数的期望按 Golden 推导：两个解析器共享一条 MAC 接收流并观察全部注入帧，因此各自也会拒绝属于对方路径的帧（业务帧 2 个、管理帧 53 个、非授权对端 1 个）。服务计数改按"实际产生应答的用例"而非"全部用例"计算：50 个 SNMP 向量中有 6 个异常请求按协议保持静默。时务请求用例不带 GMII 输入，注入帧数与用例数相差 1，相关推导同步修正。

## 顶层多驱动静态检查

`scripts/check_top_drivers.py` 解析模块端口方向与顶层实例连接，报告同一网被多个输出驱动的组合，并内置自检样例。对 `rtl/afdx_stage2_top.v`（5 个实例）、`rtl/afdx_stage2_mgmt_top.v`（14 个实例）与 `rtl/AFDX_top.v`（3 个实例）的检查结果均为 0 冲突；对修复前连接形式的临时副本检查报出 `biz_vlid` 同时被 `afdx_multi_vl_echo_queue` 与 `afdx_multi_vl_rx_parser` 驱动，退出码 1，表明该检查具备检出能力。

## 未完成与未验证

系统级 sysUpTime 由集成测试输入覆盖，以复用 SNMP 单元向量；真实 10 ms TimeTicks 计数器仅在未覆盖时生效，尚未用自由运行计数器做系统级核对。冷启动 Trap 未接入（`trap_start` 固定为 0）。时务路径目前只覆盖一次正常交换，时务 VL 的 BAG、连续多次交换、系统级超时与异常应答恢复均在单元级验证、未在系统级覆盖。管理族目前只有 SNMPv1，615A 加卸载尚未实现。系统级 100 Mbps 吞吐、整体最坏延时与抖动、系统时间精度、综合后网表的管理路径回归、EQ6 原生等价性均 NOT VERIFIED。
